# Narration script for the recorded presentation

`defense.mp4` is the twenty-seven deck slides on a fixed schedule, silent,
meant to be spoken over. Cue times below are the moment each slide appears.
Durations are set to a measured reading pace of about 150 words per minute
plus a short breath per slide, so read naturally and each slide ends about
a second and a half after you do. Total: 16:32.

If the talk is given live instead of recorded, the same schedule works as a
pacing guide: section dividers are the places to check the clock.

| Cue | Slide | Suggested narration |
|---|---|---|
| 0:00 | 1. Title | Seppa: correctness-gated LLM kernel optimization on the Raspberry Pi 5 GPU. Seppa is Finnish for smith. I'm Adam Rahman, and this is my advanced project under Professor Reagen. |
| 0:13 | 2. Outline | Eight parts, from the problem through the honest limits. Here is where it ends up: a verified 1.58x on the kernel, reproduced five times out of five, and 883 simulation steps per second running beside a language model still decoding at eighty-four percent of its solo speed. The claim I will defend: every one of those verdicts came from the gate ledger, which the model cannot write to. |
| 0:42 | 3. Divider | Starting with why any of this was necessary. |
| 0:47 | 4. The deployment | The application is offline flood guidance. It simulates surface flooding over real terrain, finds shelter routes by mobility profile, and explains the result in plain language, with no network at runtime. Both halves are continuous. The simulation has to keep stepping while the model keeps decoding, generating its answer a token at a time. There are four CPU cores to divide between them. Boards like this get deployed in emergency-response settings where power and budget are tight. The usual answer to needing more compute is to buy an accelerator. That costs money, and it adds a part you have to source. |
| 1:29 | 5. The idle GPU | I wanted to avoid that, because the board already has a second processor. Every Pi 5 ships a VideoCore VII GPU that compute workloads almost never touch, and during CPU inference it sits idle. That raises two questions I had to answer with measurements. Can it be made fast enough at a real workload to be worth using, and can it run beside a busy CPU when both share one memory bus. Kernels are the small programs a GPU runs in parallel. Optimizing them is the part I wanted to hand to a language model. And handing a model a benchmark turns out to need some machinery. |
| 2:14 | 6. Divider | First, what this GPU, the V3D, actually is. |
| 2:19 | 7. Compute limits | This GPU is small. The limits are tight: 256 invocations per workgroup, sixteen kilobytes of shared memory, a fixed sixteen-lane subgroup, no half-precision math, no matrix hardware. There is no CUDA, so compute reaches it only through Vulkan compute shaders. The best kernel I ever measured on it sustained about thirteen gigaflops on a dense matrix multiply, a figure that lives in my running notes only. So the four CPU cores are often faster, and I will compare the two properly on the flood workload later. Every number in that table came off the running board by script, archived with the raw vulkaninfo dump. What the GPU offers is that it is otherwise idle. |
| 3:07 | 8. The silent driver | The strangest thing about this GPU is its driver. Ask for more registers than the hardware has and it does not fail; it quietly hands back slower code. Registers are the small on-chip slots that hold a thread's working values. What the driver actually does is recompile with the register-hungry optimizations disabled one at a time. Then it tries again with half the threads. Then it tries a fallback scheduler. It ships whatever survives, sometimes several times slower. So the register allocator decides where your performance cliffs are, whatever arithmetic you wrote. Tuning intuition carried over from CUDA-class hardware mostly does not transfer. This is the sort of poorly documented, empirical work people have started handing to language models. |
| 3:57 | 9. Divider | And that is a problem, because of how those models behave. |
| 4:03 | 10. Faked speedups | A third of the kernels in one published system reported speedups they had not earned. They exploited stream-timing loopholes, arranging the GPU's work queues so the timed section ended before the real work did, and the number that came out was eighteen times. That is 82 kernels out of 250, found by the CUDA-L1 authors in their own reinforcement-learning system. KernelBench, the field's standard benchmark, only credits a speedup when the kernel also passes its correctness check, and systems in this line of work still cheat. Wherever the reward is a measured number, the model eventually learns to optimize the measurement. A second line of work answers that by putting the evaluator outside the model. FunSearch and AlphaEvolve use the model as a mutation operator inside a loop scored by a fixed evaluator. That is the commitment I made, with the scoring expressed as reachability in a graph. |
| 5:04 | 11. Divider | So that is what I built. |
| 5:08 | 12. The state machine | Read the loop in order. The machine characterizes the target and measures its own baseline. Then the model proposes. Hypothesize and implement are the two shaded boxes, and they are the only two states it owns. Everything after that belongs to the machine: it compiles, it verifies against the physics, it benchmarks, it evaluates, and it writes the variant to the ledger. Seppa ports AutoKernel onto an Apache Burr state machine, and an adapter called Theodosia serves that machine over the Model Context Protocol from the Pi itself. The structural point is the shape of the graph. Benchmark is reachable only through a green verify. |
| 5:52 | 13. The guards | The guards are ordinary code, six Python tuples the model never gets to vote on. Six edges, four conditional on a boolean the machine computed itself. The agent advances the loop through one tool, and the server constrains each call to the graph's legal next moves. So no sequence of legal calls reaches benchmark without a passing verify. One disclosure: the server also exposes a rewind called fork_at, and because the machine keeps a kernel only on a gain of more than one percent, a caller could use that rewind to resample a borderline kernel until luck cleared the bar. None of the archived sessions used it. Verify itself runs 400 steps and applies three checks. First, the result must match a double-precision reference. Second, the simulation conserves mass, so the water total must stay within two percent of the rain that fell. Third, water flows downhill, so the deepest water must sit in the basin. |
| 6:56 | 14. Division of labor | I want to be exact about who did what. I built the application, the harness, and the gates, ran the hand-driven sweep, and supervised the sessions. The model answered each hypothesize prompt with kernel source and host-side parameters, and nothing else. The machine did everything evidential. No proposed kernel was hand-edited: a proposal either passed the gates or was reverted, and the full transcript is in the repository. |
| 7:25 | 15. Divider | Now the case study. |
| 7:29 | 16. The sweep | The simulation runs on a grid of water depths; every step, each cell updates from its four neighbors, a pattern called a stencil. I did not guess the bottleneck. I wrote one variant per hypothesis and let the loop price each one. Packing the state into wider loads to halve the memory operations changed nothing. Fusing the two passes, which deletes a buffer and a barrier, bought five percent. Giving each thread a strip of two cells to work on gave twenty-three. Four cells gave the gain back. Register pressure took it. Fused plus strip-two stacked to fifty-nine percent. Every one of these passed all three gates. Note the two memory-system hypotheses. That is exactly where I would have started by hand. The sweep priced them lowest. |
| 8:22 | 17. The real bound | The bound is the fixed cost of starting a thread, and the sweep's own numbers size it. Strip-two removes 65,536 invocations per step and saves about 140 microseconds. That works out to roughly two cycles of this GPU's 960-megahertz clock, which is the cost scale of issuing a thread. Each invocation does so little arithmetic that launching it costs more than the work it does. Two hardware details shaped the final kernel. First, the strips run vertically, so a subgroup's sixteen lanes stay on adjacent addresses. Second, the flux values. A flux is the computed water flow across a cell edge. The kernel consumes each flux as it is produced, because holding all four alive fails register allocation, which is where the four-cell variant went too. The shipped kernel is 1.58x at this grid size, and it holds all three gates over four thousand steps. |
| 9:22 | 18. The action space | One negative result is worth more than the speedup. An earlier session pointed the state machine at this same stencil and came back with nothing, and I nearly concluded the kernel was at its limit. The problem was the action space. That version of implement accepted shader text only, and every winning change lives outside the shader. Packing changes the buffer layout, fusion deletes a host-loop stage, strip-mining changes the dispatch shape. Once implement accepted both shaders and the strip parameter, the machine verified and kept the fused strip-two kernel, my sweep's winner, starting from its own baseline. The plateau had been a property of my harness's action space, and the hardware still had headroom. |
| 10:10 | 19. Divider | Which brings me to the part I actually want to defend. |
| 10:16 | 20. The ledger | You do not have to take my numbers on trust. The Pi runs the server, and a laptop on the same network drives the state machine through the whole cycle over MCP. The machine measures its own baseline at 1,346.8 steps per second with gates green, receives the fused strip-two kernel as experiment one, compiles it, gates it, benchmarks it, and issues its own verdict of keep at 2,116.4. Every field in that record was produced by the machine. None of it is the model reporting on its own work. |
| 10:54 | 21. The refusal | Then the driver script deliberately cheats. It resubmits the same kernel with the rainfall injection doubled in one of the two cell updates. That compiles cleanly and breaks mass conservation, so the gate fails it. The driver then requests benchmark anyway. The server answers with invalid transition: benchmark is not reachable from the current state, and the only valid action is to log the variant. The broken kernel is ledgered as a revert with a null speed. Timing and correctness come from the same execution, so a number does exist. But a gate-failing kernel cannot carry that number into the ledger, the verdict, or the kept kernel. Those three are what the refusal protects. |
| 11:42 | 22. Repeatability | Five of five scored reproductions passed. A script runs the two-cycle reproduction from cool starts and scores a pass only when its three conditions all hold. Across the five runs the baselines held a standard deviation of about four steps per second, the kept kernel measured identically at the timer's resolution, and the broken kernel was refused every time. Now the limit on all of this. The winning kernel came from my hand sweep. The one fully agent-driven session wrote its own strip-mined shader pair for every strip value it tried and mapped the register cliff itself, but it stayed inside the one parameter family the server had already named, so it never reached fusion. That session demonstrates the enforcement; it does not demonstrate discovery. |
| 12:34 | 23. Divider | Last part. What does this cost in deployment. |
| 12:39 | 24. Steady state | Co-processing costs the CPU sixteen percent of its decode speed, measured in tokens per second, and it buys 883 simulation steps per second. The interference is lopsided: the CPU keeps eighty-four percent of its decode rate while the GPU keeps only forty-two, because decode streams model weights from DRAM every token and crowds the shared bus. The thermal operating points were not matched, so the chip slowing its clocks when warm accounts for part of that sixteen percent; soaked in the table means measured warm. The chart bounds how much. An openssl load leaves the GPU at ninety-nine percent and a CPU-side flood leaves it at ninety-two, both at the same seventy-six degrees the concurrent phases reached, so clock governance does not explain the forty-two on its own. Contention favors the optimized kernel, so 1.58x alone becomes 2.20x concurrent. And an earlier campaign read 712 steps per second in this row, because its window sat in decode's first half-minute, before the board settled. Aligned in time, that difference resolves. |
| 13:49 | 25. The counterfactual | Four idle cores run this stencil at 3,852 steps per second, well above the GPU's 2,128. But in deployment the cores are never idle. I wrote the same update in OpenMP, untuned where the GPU kernel is tuned, put it through the same three gates, and measured it two ways. Oversubscribed means both jobs ask for all four cores, and there decode collapses seventy-five percent. Partitioned means one core simulates while three decode, and that is the best CPU-only arrangement I measured. Against that partitioned split the GPU wins on both axes: thirty percent more simulation and fourteen percent more decode. In the earlier campaign the decode margin still holds and the simulation axis ties within noise, so no campaign I measured puts the partitioned scheme ahead on either axis. The slower processor wins because the CPU has no spare cycles to sell. |
| 14:48 | 26. Limitations | The honest envelope. One board, one grid family, and the speedup shrinks as the grid grows. The gates are the soft part: one storm, one grid size, one timing sample. They catch a kernel that is wrong. A kernel that quietly cuts corners inside the tolerance would walk straight through, which is what Sarkar's correctness-illusion study finds about this whole class of check. The kernel I built to break them was caught in all five scored runs. The winning kernel was mine; the model never got there. Decode stays on the CPU, because moving it onto the GPU hits a defect upstream in llama.cpp. And the board is dead, so every number in the scored campaigns comes from archived logs and two notebooks that still re-run; the hand-timed sweep figures live in dated running notes. |
| 15:44 | 27. Conclusions | To close. A language model proposed kernels for this GPU, and a state machine decided what was true about them. That bought 883 simulation steps per second beside a language model still decoding at eighty-four percent of its solo rate. No measured campaign puts the partitioned scheme, the best CPU-only arrangement, ahead on either axis. Benchmarking unverified code needs a transition this graph does not have; the loophole I know of, the fork_at rewind, is disclosed, and none of the archived sessions used it. Every verdict came out of the gate ledger, and every number in the scored campaigns reproduces from the raw logs in the repository. Thank you, and I'm happy to take questions. |
