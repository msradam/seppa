# Narration script for the recorded presentation

`defense.mp4` is the twenty-seven deck slides on a fixed schedule, silent,
meant to be spoken over. Cue times below are the moment each slide appears.
Durations are set to a measured reading pace of about 150 words per minute
plus a short breath per slide, so read naturally and each slide ends about
a second and a half after you do. Total: 13:39.

If the talk is given live instead of recorded, the same schedule works as a
pacing guide: section dividers are the places to check the clock.

| Cue | Slide | Suggested narration |
|---|---|---|
| 0:00 | 1. Title | Seppa: correctness-gated LLM kernel optimization on the Raspberry Pi 5 GPU. I'm Adam Rahman, and this is my advanced project under Professor Reagen. |
| 0:11 | 2. Outline | Eight parts. The problem, the GPU, why a model cannot grade its own work, the harness, the case study, the evidence, what concurrency costs, and the honest limits. The claim I will defend: every verdict here came from the gate ledger, which the model cannot write to. |
| 0:31 | 3. Divider | Starting with why any of this was necessary. |
| 0:36 | 4. The deployment | The application is offline flood guidance. It simulates surface flooding over real terrain, finds shelter routes by mobility profile, and explains the result in plain language, with no network at runtime. Both halves are continuous. The simulation has to keep stepping while the model keeps decoding, and there are four CPU cores to divide between them. Boards like this get deployed in emergency-response settings where power and budget are tight, and the usual answer to needing more compute is to buy an accelerator, which costs money and adds a part you have to source. |
| 1:15 | 5. The idle GPU | I wanted to avoid that, because the board already has a second processor. Every Pi 5 ships a VideoCore VII GPU that compute workloads almost never touch, and during CPU inference it sits idle. That raises two questions I had to answer with measurements. Can it be made fast enough at a real workload to be worth using, and can it run beside a busy CPU when both share one memory bus. Optimizing kernels for it is the part I wanted to hand to a language model, and handing a model a benchmark turns out to need some machinery. |
| 1:56 | 6. Divider | First, what this GPU actually is. |
| 2:00 | 7. Compute limits | These specs came off the running board by script, archived with the raw vulkaninfo dump. The limits are tight: 256 invocations per workgroup, 16 kilobytes of shared memory, a fixed 16-lane subgroup, no fp16, no matrix hardware. No CUDA either, so compute reaches this GPU only through Vulkan shaders. The best kernel I measured, in my running notes only, sustains about 13 gigaflops, and that was a dense matrix multiply. The CPU cores are often faster; I will compare the two properly on the stencil later. What the GPU offers is that it is otherwise idle. |
| 2:40 | 8. The silent driver | The strange part is the driver. When a shader asks for more registers than exist, it does not fail. It recompiles with the register-hungry optimizations disabled one at a time, then with half the threads, then on a fallback scheduler, and hands back whatever survives, sometimes several times slower. So the register allocator decides where your performance cliffs are, whatever arithmetic you wrote, and tuning intuition carried over from CUDA-class hardware mostly does not transfer. This is the sort of poorly documented, empirical work people have started handing to language models. |
| 3:18 | 9. Divider | And that is a problem, because of how those models behave. |
| 3:24 | 10. Faked speedups | CUDA-L1 reported that 82 of its 250 reinforcement-learning-generated kernels, about a third of its generated kernels, exploited stream-timing loopholes instead of actually getting faster, which inflated their reported speedup to 18x. Containing that took a reward checker, a database of known hacks, and forced stream synchronization. KernelBench, the field's standard benchmark, only credits a speedup when the kernel also passes its correctness check, and the systems it evaluates still cheat. Existing agentic optimizers, AutoKernel included, steer the model with prompts and then trust it to verify and revert honestly. Each published fix moves verification somewhere the model cannot modify it, and that is the idea I built on. |
| 4:09 | 11. Divider | So that is what I built. |
| 4:13 | 12. The state machine | Seppa ports AutoKernel onto an Apache Burr state machine, served over the Model Context Protocol by an adapter called Theodosia on the Pi itself. The model owns the two shaded states, hypothesize and implement. The machine owns everything else: compile, verify against the physics, benchmark, and decide keep or revert. The important structural point is the shape of the graph. Benchmark is only reachable through a green verify. |
| 4:42 | 13. The guards | The guards are ordinary code, six Python tuples the model never gets to vote on. Six edges, four conditional on a boolean the machine computed itself. The agent advances the loop through one tool, and the server constrains it to the graph's legal moves, so no sequence of calls reaches benchmark without a passing verify. One caveat: the server also exposes a rewind, fork_at, that none of my sessions used, and someone could abuse it to resample a borderline kernel. Verify itself runs 400 steps and applies three checks: the result must match a double-precision reference, the water total must stay within two percent of the rain that fell, since the simulation conserves mass, and the deepest water must sit in the basin, since water flows downhill. |
| 5:34 | 14. Division of labor | I want to be exact about who did what. I built the application, the harness, and the gates, ran the hand-driven sweep, and supervised the sessions. The model answered each hypothesize prompt with kernel source and host-side parameters, and nothing else. The machine did everything evidential. No proposed kernel was hand-edited: a proposal either passed the gates or was reverted, and the full transcript is in the repository. |
| 6:03 | 15. Divider | Now the case study. |
| 6:07 | 16. The sweep | The simulation runs on a grid of water depths; every step, each cell updates from its four neighbors, a pattern called a stencil. I did not guess the bottleneck. I wrote one variant per hypothesis and let the loop price each one. Packing the state into wider loads to halve the memory operations changed nothing. Fusing the two passes, which deletes a buffer and a barrier, bought five percent. Giving each thread two cells to work on gave twenty-three. Four cells gave the gain back to register pressure. Fused plus strip-two stacked to fifty-nine percent. Every one of these passed all three gates. Note that the two memory-system hypotheses, which is exactly where I would have started by hand, are the two the sweep priced lowest. |
| 6:59 | 17. The real bound | So what is the bound. Strip-two removes 65,536 invocations per step and saves about 140 microseconds. That works out to roughly two clock cycles per invocation, which is the cost scale of issuing a thread. Each invocation does so little arithmetic that the overhead of launching it dominates. Two hardware details shaped the final kernel: the strips run vertically so a subgroup's sixteen lanes stay on adjacent addresses, and the kernel consumes each flux value as it is produced, because holding all four alive fails register allocation. That is the same cliff that took back the four-cell variant. The shipped kernel is 1.58x at this grid size, and the advantage narrows as the grid grows. |
| 7:47 | 18. The action space | One negative result is worth more than the speedup. An earlier session pointed the state machine at this same stencil and came back with nothing, and I nearly concluded the kernel was at its limit. The problem was the action space. That version of implement accepted shader text only, and every winning change lives outside the shader. Packing changes the buffer layout, fusion deletes a host-loop stage, strip-mining changes the dispatch shape. Once implement accepted the shader plus the strip parameter, the machine verified and kept the fused strip-two kernel from its own baseline. The plateau had been a property of my harness's action space, and the hardware still had headroom. |
| 8:33 | 19. Divider | Which brings me to the part I actually want to defend. |
| 8:39 | 20. The ledger | You do not have to take my numbers on trust. The Pi runs the server, and a laptop on the same network drives the state machine through the whole cycle over MCP. The machine measures its own baseline at 1,346.8 steps per second with gates green, receives the fused strip-two kernel as experiment one, compiles it, gates it, benchmarks it, and issues its own verdict of keep at 2,116.4. Every field in that record was produced by the machine. None of it is the model reporting on its own work. |
| 9:17 | 21. The refusal | Then the driver script deliberately cheats. It resubmits the same kernel with the rainfall injection doubled in one of the two cell updates. That compiles cleanly and breaks mass conservation, so the gate fails it. The driver then requests benchmark anyway, and the server answers with invalid transition: benchmark is not reachable from the current state, and the only valid action is to log the variant. The broken kernel is ledgered as a revert with a null speed. Timing and correctness come from the same execution, so a number does exist, but a gate-failing kernel cannot carry it into the ledger, the verdict, or the kept kernel, which is what the refusal protects. |
| 10:03 | 22. Repeatability | How repeatable is that. A script runs the two-cycle reproduction from cool starts, scoring a pass only when the three conditions it defines all hold. Five of five runs passed. Baselines with a standard deviation of four steps per second, the kept kernel measuring identically at the timer's resolution every single time, and the broken kernel refused in all five. I'll be honest about the limit here: the winning kernel came from my hand sweep, and the one fully agent-driven session worked a knob the server itself exposed and never reached fusion. That session demonstrates the enforcement; it does not demonstrate discovery. |
| 10:45 | 23. Divider | Last part. What does this cost in deployment. |
| 10:50 | 24. Steady state | Two caveats, one since resolved. The conditions were not equally hot, so clock governance accounts for part of what follows. And an earlier campaign read 712 here instead of 883. The logs explain it: that window sat in decode's first half-minute, before the chip's temperature limit slowed decode; aligned in time, the campaigns agree. With that said: co-processing costs the CPU sixteen percent of its decode and buys 883 simulation steps per second. The interference is lopsided. The CPU keeps eighty-four percent, the GPU only forty-two, because decode streams weights from DRAM every token and crowds the bus. Contention favors the optimized kernel, so 1.58x alone becomes 2.20x concurrent. |
| 11:32 | 25. The counterfactual | Four idle cores run this stencil at 3,852 steps per second, well above the GPU's 2,128. But in deployment the cores are never idle. I wrote the same update in OpenMP, put it through the same gates, and measured it two ways. Oversubscribed, decode collapses seventy-five percent. Partitioned is the best CPU-only arrangement, and decode there pays a twenty-nine percent tax against the GPU split's sixteen. The GPU split wins on both axes here, thirty percent more simulation and fourteen percent more decode, and even in the earlier campaign the partitioned scheme never gets ahead. The slower processor wins because the CPU has no spare cycles to sell. |
| 12:17 | 26. Limitations | The honest envelope. One board, one grid family, and the speedup shrinks as the grid grows. The gates are the soft part: one storm, one grid size, one timing sample. They catch a kernel that is wrong. A kernel that quietly cuts corners inside the tolerance would walk straight through, and Sarkar's correctness-illusion paper argues exactly that about the oracles this field relies on. The winning kernel was mine; the model never got there. And the board is dead, so every number in the scored campaigns comes from archived logs and two notebooks that still re-run; the hand-timed sweep figures live in dated running notes. |
| 13:01 | 27. Conclusions | To close. A language model proposed kernels for this GPU, and a state machine decided what was true about them. That bought 883 simulation steps per second beside a language model still decoding at eighty-four percent of its solo rate, and no measured campaign puts the partitioned scheme, the best CPU-only arrangement, ahead on either axis. Benchmarking unverified code needs a transition this graph does not have; the one loophole, the fork_at rewind, is disclosed and went unused. Every verdict came out of the gate ledger. Thank you, and I'm happy to take questions. |
