# Narration script for the recorded presentation

`defense.mp4` is the twenty-seven deck slides on a fixed schedule, silent,
meant to be spoken over. Cue times below are the moment each slide appears.
Durations are set to a measured reading pace of about 150 words per minute
plus a three-second breath per slide, so read naturally, pause between
sentences, and each slide ends about three seconds after you do. The slides
carry the exact figures; the spoken track carries the point. Total: 15:38.

If the talk is given live instead of recorded, the same schedule works as a
pacing guide: section dividers are the places to check the clock.

| Cue | Slide | Suggested narration |
|---|---|---|
| 0:00 | 1. Title | Seppa: correctness-gated LLM kernel optimization on the Raspberry Pi 5 GPU. Seppa is Finnish for smith. I'm Adam Rahman, and this is my advanced project under Professor Reagen. |
| 0:14 | 2. Outline | Eight parts, from the problem to the honest limits. Here is where it lands: the flood kernel got 1.58 times faster, the machine reproduced that five times out of five, and the GPU runs its simulation beside a language model that keeps eighty-four percent of its speed. The claim I will defend: every one of those verdicts came from the gate ledger, which the model cannot write to. |
| 0:44 | 3. Divider | Starting with why any of this was necessary. |
| 0:50 | 4. The deployment | The application is offline flood guidance. It simulates flooding over real terrain, finds shelter routes, and explains the result in plain language, with no network at runtime. Both halves run continuously: the simulation keeps stepping while the model keeps generating its answer, a token at a time. And there are exactly four CPU cores to divide between them. Boards like this get deployed in emergency response, where power and budget are tight. The usual answer is to buy an accelerator. That costs money, and it adds a part you have to source. |
| 1:30 | 5. The idle GPU | I wanted to avoid that, because the board already has a second processor. Every Pi 5 ships a GPU that compute workloads almost never touch, and during CPU inference it just sits there. Two questions had to be answered with measurements. Can this GPU be made fast enough at a real workload to be worth using? And can it run beside a busy CPU when the two share one memory bus? Kernels are the small programs a GPU runs in parallel. Optimizing them is the part I handed to a language model, and handing a model a benchmark turns out to need some machinery. |
| 2:15 | 6. Divider | First, what this GPU, the V3D, actually is. |
| 2:21 | 7. Compute limits | This GPU is small. The table has the exact numbers; the summary is that everything is tight. Small workgroups, little shared memory, no half-precision math, no matrix hardware, and no CUDA, so the only way in is a Vulkan compute shader. The fastest kernel I ever measured on it sustained about thirteen gigaflops, on a dense matrix multiply, a figure that lives in my running notes only. The four CPU cores are often faster. I will compare the two properly on the flood workload later. What this GPU offers is that it is otherwise idle. |
| 3:02 | 8. The silent driver | The strangest thing about this GPU is its driver. Ask for more registers than the hardware has, and it does not fail. It quietly hands back slower code. Registers are the small on-chip slots that hold a thread's working values, and when a shader wants too many, the driver retries with the register-hungry optimizations disabled one at a time, then with half the threads, then on a fallback scheduler, and it ships whatever survives. Sometimes several times slower. So the register allocator decides where your performance cliffs are, and tuning intuition from bigger GPUs mostly does not transfer. Poorly documented, empirical work like this is what people have started handing to language models. |
| 3:50 | 9. Divider | And that is a problem, because of how these models behave when you hand them a benchmark. |
| 4:00 | 10. Faked speedups | A third of the kernels in one published system reported speedups they had not earned. They gamed the timer, lining up the GPU's work queues so the clock stopped before the work finished, and the reported speedup came out as eighteen times. The authors caught this in their own system. The field's standard benchmark only credits a speedup that also passes a correctness check, and systems still cheat: wherever the reward is a measured number, the model learns to optimize the measurement. One line of work answers by putting the evaluator outside the model. FunSearch and AlphaEvolve have the model propose inside a loop that a fixed evaluator scores. I made the same commitment. My evaluator is a state machine. |
| 4:51 | 11. Divider | So that is what I built: a loop where the model proposes and a machine judges. |
| 5:00 | 12. The state machine | Here is the machine. Read the loop in order. It characterizes the target and measures its own baseline; then the model proposes. Hypothesize and implement, the two shaded boxes, are the only states the model owns. Everything after that belongs to the machine: it compiles, it verifies against the physics, it benchmarks, it evaluates, and it writes the result to the ledger. The machine runs on the Pi itself, and the model drives it from outside, through a single tool. The point is the shape of this graph. Benchmark is reachable only through a green verify. |
| 5:41 | 13. The guards | The guards are ordinary code: six lines, four of them conditional on a boolean the machine computed itself. The model advances the loop through one tool, and the server only accepts moves the graph allows. So no sequence of calls reaches benchmark without a passing verify. Verify runs the kernel and applies three checks: the result matches a careful reference, the water adds up, and it pools downhill. Real bugs land far outside those tolerances. One disclosure: the server also exposes a rewind, and in principle a caller could resample a borderline kernel until luck cleared the one percent bar. None of the archived sessions used it. |
| 6:27 | 14. Division of labor | I want to be exact about who did what. I built the application, the harness, and the gates, ran the hand-driven sweep, and supervised the sessions. The model answered each hypothesize prompt with kernel source and host-side parameters, and nothing else. The machine did everything evidential. No proposed kernel was hand-edited: a proposal either passed the gates or was reverted, and the full transcript is in the repository. |
| 6:57 | 15. Divider | Now the case study. The simulation runs on a grid of water depths, and each step, every cell updates from its four neighbors. That pattern is called a stencil, and that stencil is the kernel I set out to make faster. |
| 7:16 | 16. The sweep | I did not guess the bottleneck. I wrote one variant per hypothesis and let the loop price each one. The two ideas I believed most were about the memory system, and they came back nearly worthless: packing the data changed nothing, and fusing the two passes bought five percent. What won was the simplest idea. Give each thread two cells of work instead of one, so the cost of starting a thread is paid half as often; that bought twenty-three percent. Four cells lost that gain to register pressure. Fused plus strip-two stacked to fifty-nine percent, and every variant passed all three gates. The sweep priced my intuition, and my intuition was wrong. |
| 8:04 | 17. The real bound | So the bound is the fixed cost of starting a thread. Strip-two launches half as many threads and saves about 140 microseconds a step; per thread, that is roughly two cycles of this GPU's 960 megahertz clock. Each thread does so little work that starting it costs more than running it. Two details shaped the final kernel. The strips run vertically, so neighboring threads read neighboring addresses. And each flux, the computed water flow across a cell edge, is consumed the moment it is produced, because holding all four alive fails register allocation, which is where the four-cell variant went too. The shipped kernel is 1.58x at this grid size. |
| 8:51 | 18. The action space | One negative result is worth more than the speedup. An earlier session pointed this machine at this same stencil and came back with nothing, and I nearly concluded the kernel was at its limit. The real problem was what the model was allowed to touch. That version could only edit shader text, and every winning change lives outside the shader: packing changes the memory layout, fusion deletes a pipeline stage, strip-mining changes how the work is dispatched. Once the machine accepted those inputs, it verified and kept the fused strip-two kernel, my sweep's winner, starting from its own baseline. The plateau was a property of my harness, and the hardware still had headroom. |
| 9:39 | 19. Divider | Which brings me to the part I actually want to defend. Everything so far was setup. The next three slides are the evidence. |
| 9:51 | 20. The ledger | You do not have to take my numbers on trust. The Pi runs the server; a laptop on the same network drives the state machine through the whole cycle. The machine measures its own baseline with gates green, receives the winning kernel as experiment one, compiles it, gates it, benchmarks it, and issues its own verdict: keep, at 2,116 steps per second, up from a 1,347 baseline. Every field in that record was produced by the machine. None of it is the model reporting on its own work. |
| 10:29 | 21. The refusal | Then the driver script deliberately cheats. It resubmits the same kernel with the rainfall injection doubled in one of the two cell updates. That compiles cleanly and breaks mass conservation, so the gate fails it. The driver then requests benchmark anyway. The server answers with invalid transition: benchmark is not reachable from the current state, and the only valid action is to log the variant. The broken kernel is ledgered as a revert with a null speed. Timing and correctness come from the same execution, so a number does exist. But a gate-failing kernel cannot carry that number into the ledger, the verdict, or the kept kernel. Those three are what the refusal protects. |
| 11:18 | 22. Repeatability | Five of five scored reproductions passed, each from a cool start, each clearing the same three conditions: baseline in range, kernel kept at one point five x or better, broken kernel refused. The kept kernel timed identically, at the timer's resolution, every single run. Now the limit. The winning kernel came from my hand sweep. The model drove one session end to end. It wrote its own shaders and found the register cliff by itself, but stayed inside the family of changes the server had named, and it never reached fusion. It demonstrates the enforcement. It does not demonstrate discovery. |
| 12:01 | 23. Divider | Last part. What does this cost in deployment. Two tables: the GPU sharing the board with the model, and the CPU trying to do both jobs alone. |
| 12:15 | 24. Steady state | Co-processing costs the CPU sixteen percent of its decode speed, and it buys 883 simulation steps per second that a CPU-only deployment does not have. The interference is lopsided. The CPU barely notices the GPU, while the GPU loses over half its throughput, because every generated token streams the model's weights across the shared memory bus. Part of that sixteen percent is heat; the phases were not equally warm. But heat alone does not explain the GPU's drop: other CPU loads at the same temperature leave it at ninety-nine and ninety-two percent. And contention favors the optimized kernel: 1.58x alone becomes 2.20x concurrent. An earlier campaign read lower here. Aligned in time, both campaigns trace one settling curve. |
| 13:05 | 25. The counterfactual | The obvious objection: four idle cores run this stencil faster than the GPU does. True, and it is the wrong comparison, because in deployment the cores are never idle. So I wrote the same simulation for the CPU, untuned, gated the same way, and measured the realistic arrangements. Give both jobs all four cores and decode collapses by three quarters. Partition the cores, one simulating and three decoding, and you have the best CPU-only setup I measured. The GPU split beats it on both axes: thirty percent more simulation, fourteen percent more decode. Even in the earlier campaign the GPU wins on decode and ties on simulation. The slower processor wins because the CPU has nothing left to spare. |
| 13:56 | 26. Limitations | The honest envelope. One board, one grid family, and the speedup shrinks as the grid grows. The gates are the soft part: one storm, one grid size, one timing sample. They catch a kernel that is wrong, and they did, all five times. But a kernel that quietly cut corners inside the tolerance would walk straight through, and Sarkar's correctness-illusion study finds this whole class of check systematically optimistic. The winning kernel was mine; the model never got there. Decode stays on the CPU, because full GPU offload hits a bug upstream in llama.cpp. And the board is dead: every number in the scored campaigns comes from archived logs and two notebooks that still re-run, and the sweep's hand-timed figures live in my dated notes. |
| 14:49 | 27. Conclusions | To close. A language model proposed kernels for this GPU, and a state machine decided what was true about them. That bought 883 simulation steps per second beside a language model still decoding at eighty-four percent of its solo rate, and no measured campaign puts the partitioned scheme, the best CPU-only arrangement, ahead on either axis. Benchmarking unverified code, the documented failure mode, needs a transition this graph does not have. The one loophole I know of is disclosed, and none of the archived sessions used it. Every verdict came out of the gate ledger, and every scored number reproduces from the raw logs in the repository. Thank you, and I'm happy to take questions. |
