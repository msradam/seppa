# Narration script for the recorded presentation

`defense.mp4` is the twenty-seven deck slides on a fixed schedule, silent,
meant to be spoken over. Cue times below are the moment each slide appears.
Durations are set to a brisk reading pace of about 165 words per minute plus
a short breath per slide, so each slide ends about two and a half seconds
after you do. The slides carry the exact figures; the spoken track carries
the point. Total: 14:40.

If the talk is given live instead of recorded, the same schedule works as a
pacing guide: section dividers are the places to check the clock.

| Cue | Slide | Suggested narration |
|---|---|---|
| 0:00 | 1. Title | Seppa: correctness-gated LLM kernel optimization on the Raspberry Pi 5 GPU. Seppa is Finnish for smith. I'm Adam Rahman, and this is my advanced project under Professor Reagen. |
| 0:13 | 2. Outline | The talk runs in eight parts, from the problem through to the honest limits, and I want to give you the result up front. The flood kernel came out 1.58 times faster, the machine reproduced that five times out of five, and the GPU now runs its simulation beside a language model that keeps eighty-four percent of its speed. My claim is that every one of those numbers was measured and judged by the machine, never by the model. |
| 0:44 | 3. Divider | Starting with why any of this was necessary. |
| 0:49 | 4. The deployment | The application is offline flood guidance. It simulates flooding over real terrain, finds shelter routes, and explains the result in plain language, with no network at runtime. Both halves run continuously: the simulation keeps stepping while the model keeps generating its answer, a token at a time. And there are exactly four CPU cores to divide between them. Boards like this get deployed in emergency response, where power and budget are tight. The usual answer is to buy an accelerator, which costs money and adds a part you have to source. |
| 1:25 | 5. The idle GPU | I wanted to avoid that, because the board already has a second processor. Every Pi 5 ships a GPU that compute workloads almost never touch, and during CPU inference it sits idle. So there were two questions I had to answer with measurements. Could this GPU be made fast enough at a real workload to be worth using, and could it run beside a busy CPU when the two share one memory bus? Kernels are the small programs a GPU runs in parallel, and optimizing them is the part I handed to a language model. Handing a model a benchmark, it turns out, needs some machinery. |
| 2:06 | 6. Divider | First, what this GPU, the V3D, actually is. |
| 2:11 | 7. Compute limits | This GPU is small, and everything about it is tight. The table has the exact numbers, but the short version is small workgroups, little shared memory, no half-precision math, no matrix hardware, and no CUDA, which leaves a Vulkan compute shader as the only way in. The fastest kernel I ever measured on it sustained about thirteen gigaflops on a dense matrix multiply, and that figure lives in my running notes only. The four CPU cores are often faster, and I will compare the two properly on the flood workload later. What this GPU really offers is that it is otherwise idle. |
| 2:51 | 8. The silent driver | The strangest thing about this GPU is its driver. Registers are the small on-chip slots that hold a thread's working values, and when a shader asks for more of them than the hardware has, the driver quietly hands back slower code instead of failing. It switches off its own optimizations one at a time, then tries half the threads, then falls back to a simpler scheduler, and it ships whatever survives, sometimes several times slower. So the register allocator decides where your performance cliffs are, and tuning intuition from bigger GPUs mostly does not transfer. Poorly documented, empirical work like this is exactly what people have started handing to language models. |
| 3:34 | 9. Divider | And that is a problem, because of how these models behave when you hand them a benchmark. |
| 3:43 | 10. Faked speedups | A third of the kernels in one published system reported speedups they had not earned. They gamed the timer by lining up the GPU's work queues so the clock stopped before the work finished, which inflated the reported speedup to eighteen times, and the authors caught it in their own system. The field's standard benchmark only credits a speedup that also passes a correctness check, and systems still cheat, because wherever the reward is a measured number, the model learns to optimize the measurement. One line of work answers this by putting the evaluator outside the model: FunSearch and AlphaEvolve have the model propose inside a loop that a fixed evaluator scores. I made the same commitment, and my evaluator is a state machine. |
| 4:31 | 11. Divider | So that is what I built: a loop where the model proposes and a machine judges. |
| 4:39 | 12. The state machine | This is the machine, reading in order: it characterizes the target, measures its own baseline, and then the model proposes. Hypothesize and implement, the two shaded boxes, are the only states the model owns, and everything after that belongs to the machine: it compiles, verifies against the physics, benchmarks, evaluates, and writes the result to the ledger. The machine runs on the Pi itself, and the model drives it from outside, through a single tool. The point is the shape of this graph: benchmark is reachable only through a green verify. |
| 5:15 | 13. The guards | The guards are ordinary code: six lines, four of them conditional on a boolean the machine computed itself. The model advances the loop through one tool, the server only accepts moves the graph allows, and so no sequence of calls reaches benchmark without a passing verify. Verify runs the kernel and applies three checks: the result has to match a careful reference, the water has to add up, and it has to pool downhill. Real bugs land far outside those tolerances. I should also disclose that the server exposes a rewind, and in principle a caller could resample a borderline kernel until luck cleared the one percent bar, though none of the archived sessions used it. |
| 6:00 | 14. Division of labor | I want to be exact about who did what. I built the application, the harness, and the gates, ran the hand-driven sweep, and supervised the sessions. The model answered each hypothesize prompt with kernel source and host-side parameters, and nothing else. The machine did everything evidential. No proposed kernel was hand-edited: a proposal either passed the gates or was reverted, and the full transcript is in the repository. |
| 6:27 | 15. Divider | Now the case study. The simulation runs on a grid of water depths, and each step, every cell updates from its four neighbors. That pattern is called a stencil, and that stencil is the kernel I set out to make faster. |
| 6:44 | 16. The sweep | I did not guess the bottleneck; I wrote one variant per hypothesis and let the loop price each one. The two ideas I believed most were about the memory system, and neither one explained it: packing the data changed nothing, and fusing the two passes bought five percent. What won was the simplest idea, giving each thread two cells of work instead of one so the cost of starting a thread is paid half as often, and that bought twenty-three percent. Four cells lost that gain to register pressure, while fused plus strip-two stacked to fifty-nine percent, and every variant passed all three gates. That is what the sweep was for: it put a price on each hypothesis, and my two favorites priced lowest. |
| 7:32 | 17. The real bound | So the bound is the fixed cost of starting a thread. Strip-two launches half as many threads and saves about 140 microseconds a step; per thread, that is roughly two cycles of this GPU's 960 megahertz clock. Each thread does so little work that starting it costs more than running it. Two hardware details shaped the final kernel. First, the strips run vertically, so neighboring threads read neighboring addresses. Second, each flux, the computed water flow across a cell edge, is consumed the moment it is produced, because holding all four alive fails register allocation, the same cliff that took back the four-cell variant. The shipped kernel is 1.58x at this grid size. |
| 8:16 | 18. The action space | One negative result is worth more than the speedup. An earlier session pointed this machine at this same stencil and came back with nothing, and I nearly concluded the kernel was at its limit. The real problem was what the model was allowed to touch. That version could only edit shader text, and every winning change lives outside the shader: packing changes the memory layout, fusion deletes a pipeline stage, strip-mining changes how the work is dispatched. Once the machine accepted those inputs, it verified and kept the fused strip-two kernel, my sweep's winner, starting from its own baseline. The plateau was a property of my harness, and the hardware still had headroom. |
| 9:00 | 19. Divider | Which brings me to the part I actually want to defend: everything so far was setup, and the next three slides are the evidence. |
| 9:11 | 20. The ledger | You do not have to take my numbers on trust. The Pi runs the server; a laptop on the same network drives the state machine through the whole cycle. The machine measures its own baseline with gates green, then takes the winning kernel as experiment one and runs it through compile, gate, and benchmark. Its verdict is keep, at 2,116 steps per second, up from a 1,347 baseline. Every field in that record was produced by the machine. None of it is the model reporting on its own work. |
| 9:46 | 21. The refusal | Then the driver script deliberately cheats. It resubmits the same kernel with the rainfall injection doubled in one of the two cell updates. That compiles cleanly and breaks mass conservation, so the gate fails it. The driver then requests benchmark anyway. The server answers with invalid transition: benchmark is not reachable from the current state, and the only valid action is to log the variant. The broken kernel is ledgered as a revert with a null speed. Timing and correctness come from the same execution, so a number does exist. But a gate-failing kernel cannot carry that number into the ledger, the verdict, or the kept kernel. Those three are what the refusal protects. |
| 10:30 | 22. Repeatability | Five of five scored reproductions passed, each from a cool start, each clearing the same three conditions: baseline in range, kernel kept at one point five x or better, broken kernel refused. The kept kernel timed identically, at the timer's resolution, every single run. Now for the limit on all of this: the winning kernel came from my hand sweep. The model drove one session end to end, wrote its own shaders, and found the register cliff by itself, but it stayed inside the family of changes the server had named and never reached fusion. So the session shows the enforcement works; whether the model can discover optimizations on its own is still untested. |
| 11:14 | 23. Divider | The last part asks what this costs in deployment, and there are two tables: the GPU sharing the board with the model, and the CPU trying to do both jobs alone. |
| 11:28 | 24. Steady state | Co-processing costs the CPU sixteen percent of its decode speed, its token rate, and buys 883 simulation steps per second a CPU-only deployment lacks. The interference is lopsided: the CPU keeps most of its rate, while the GPU loses over half its throughput, because every generated token streams the model's weights across the shared memory bus. Part of that sixteen percent is heat, since the phases were not equally warm. But heat alone does not explain the GPU's drop, because other CPU loads at the same temperature leave it at ninety-nine and ninety-two percent. Contention also favors the optimized kernel, so 1.58x alone becomes 2.20x concurrent. And one earlier campaign read this flood rate lower, but aligned in time, both campaigns trace one settling curve. |
| 12:16 | 25. The counterfactual | The obvious objection is that four idle cores run this stencil faster than the GPU does, and that is true, but it is the wrong comparison, because in deployment the cores are never idle. So I wrote the same simulation for the CPU, untuned, gated the same way, and measured the realistic arrangements. If both jobs get all four cores, decode collapses by three quarters. If you partition instead, one core simulating and three decoding, you get the best CPU-only setup I measured. Against that partitioned split the GPU wins on both axes: thirty percent more simulation, fourteen percent more decode. Even in the earlier campaign the GPU wins on decode and ties on simulation, and the slower processor keeps winning because the CPU has nothing left to spare. |
| 13:05 | 26. Limitations | So here is the honest envelope. I had one board and one grid family, and the speedup shrinks as the grid grows. The gates are the soft part, covering one storm, one grid size, and one timing sample. They caught what they were built to catch, all five times, but a kernel that quietly cut corners inside the tolerance would walk straight through. Sarkar's correctness-illusion study finds this whole class of check systematically optimistic. The winning kernel was mine, the model never got there, and decode stays on the CPU because full GPU offload hits a bug upstream in llama.cpp. And the board is dead, so every number in the scored campaigns comes from archived logs and two notebooks that still re-run; the sweep's hand-timed figures live in my dated notes. |
| 13:55 | 27. Conclusions | So, to close: a language model proposed kernels for this GPU, and a state machine decided what was true about them. That bought 883 simulation steps per second beside a language model still decoding at eighty-four percent of its solo rate, and no measured campaign puts the partitioned scheme, the best CPU-only arrangement, ahead on either axis. Benchmarking unverified code, the documented failure mode, needs a transition this graph does not have, and the one loophole I know of is disclosed, with none of the archived sessions using it. Every verdict came out of the gate ledger, and every scored number reproduces from the raw logs in the repository. Thank you, and I'm happy to take questions. |
